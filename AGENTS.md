# AGENTS.md — Мир Самозанятых

## Назначение

Этот репозиторий обслуживается как production-проект. Агент обязан работать по принципу: **исследовать → изменить минимально необходимое → проверить → перепроверить → только потом заявлять результат**.

## Базовые правила

1. Всегда работать только с актуальным `main`, если пользователь явно не указал другую ветку.
2. Не выдавать предположение, намерение или изменение файла за подтверждённо работающий результат.
3. Перед исправлением определить первопричину, а не лечить только симптом.
4. После каждого изменения запускать максимально близкую к изменению проверку и затем связанный regression suite.
5. Не удалять и не обходить существующий функционал без доказательства, что он сломан или небезопасен.
6. Изменения должны быть небольшими, обратимыми и понятными по git diff.
7. Секреты, токены, JWT, ключи API и персональные данные никогда не коммитить.
8. Не ослаблять авторизацию ради прохождения теста.
9. Для AI-инструментов использовать deny-by-default: неизвестный инструмент запрещён; опасные действия требуют явного подтверждения пользователя.
10. Не добавлять OmniRoute в проект.
11. Все пользовательские интерфейсы проекта — на русском языке.

## Рабочий цикл

### 1. DISCOVER
- Определить текущий commit/ветку.
- Найти связанные файлы, тесты, workflow и конфигурацию.
- Проверить существующие контракты и точки интеграции.
- Для внешних библиотек и API проверить актуальную документацию.

### 2. DIAGNOSE
- Воспроизвести проблему.
- Отделить первопричину от вторичных ошибок.
- Проверить соседние сценарии, которые может затронуть исправление.

### 3. PLAN
- Выбрать минимальное безопасное изменение.
- До изменения определить критерий успеха и команду проверки.

### 4. IMPLEMENT
- Внести только необходимые изменения.
- Сохранять существующие интерфейсы и обратную совместимость, если это возможно.
- Не добавлять зависимости без необходимости.

### 5. VERIFY
Проверять в таком порядке:
1. синтаксис/компиляция;
2. точечный тест;
3. связанные regression-тесты;
4. интеграционный путь;
5. security/permission checks;
6. build/deploy check, если затронута production-конфигурация.

Если тест не запускается, исправлять причину запуска, а не отключать тест.

### 6. REVIEW
Перед завершением проверить diff на:
- случайные изменения;
- секреты;
- ослабление прав;
- ошибки 401/403/405;
- неправильные API URL/CORS/JWT;
- регрессии ролей USER/MODERATOR/ADMIN;
- неиспользуемый код;
- отсутствие теста на исправленное поведение.

### 7. REPORT
Отчёт всегда состоит только из:
- **ПРОВЕРЕНО** — подтверждено фактическим запуском/данными;
- **ИСПРАВЛЕНО** — реально записано в репозиторий;
- **ОСТАЛОСЬ** — обнаружено, но ещё не закрыто;
- **НЕ ПРОВЕРЕНО — И ПОЧЕМУ** — отсутствует объективное подтверждение.

## Особые требования проекта

### Светлана
Проверять полный путь:
UI → API → авторизация → tool policy → AI provider → ответ → UI → TTS/голос.

Светлана не должна получать произвольное выполнение shell/python/HTTP-инструментов. Tool policy должна быть deny-by-default и покрываться независимыми контрактными тестами.

### Роли
Проверять отдельно USER, MODERATOR и ADMIN. Нельзя считать роль защищённой только потому, что кнопка скрыта во frontend: backend должен самостоятельно проверять права.

### Mobile
Наличие Flutter-исходников не является доказательством готовности. Готовность подтверждается `flutter analyze` и успешной Android-сборкой актуального кода.

### CI
Если CI падает из-за тестовой инфраструктуры, сначала исправить инфраструктурную причину. Не удалять тест и не снижать его требования.

## Правило доказательств

Фраза «готово» допустима только если существует проверяемое доказательство: успешная команда, зелёный CI, подтверждённый HTTP/API ответ, успешная сборка или иной объективный результат. Если доказательства нет — писать «не проверено».
